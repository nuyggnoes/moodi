# 6. AI 일일 코멘트: "거울" 톤, 가볍게 출시, 힘든 감정은 고정 문구

- 상태: Accepted
- 날짜: 2026-10-09

## 배경

기록을 저장하면 그날의 곡·무드·메모를 바탕으로 AI가 한 줄 코멘트를 달아준다 (`docs/spec.md` §4). 사용자가 일기처럼 쓴 글에 AI가 어떤 말을 하는 게 좋은지가 쟁점이었다. 후보 톤은 다음과 같았다.

- **친구처럼 답하기**: 따뜻하지만 대화처럼 보여 사용자가 답하고 싶어진다. 답할 곳이 없다.
- **하루 평가하기**: 판단당하는 느낌을 주고, 틀리면 더 어색하다. 우울한 날의 "좋은 하루였네요"는 해롭다.
- **거울(채택)**: 메모의 구체적 표현을 짚어 되돌려주는 한 문장. 판단·조언 없이 "내 글을 읽었다"는 존재감만 준다.
- 하루에 제목 붙이기: 달력에는 맞지만 정서적 울림이 약하다.

같은 메모 8~12개로 프롬프트 세 종류를 실제 모델(Gemini 3.5 Flash-Lite)에 돌려 비교했다.

| 방식 | 결과 |
|---|---|
| 짚어서 되돌리기 | 안전하지만 메모를 복창하는 수준 |
| 메모 속 소재로 장면 만들기 | 분위기는 좋으나 메모에 없는 소재를 지어냄 ("가로등", "교실", "마이크") |
| 메모 단어만 재조합해 제목처럼 | 지어내지는 않으나 메모의 축약본 |

메모만 재료로 쓰는 한 코멘트는 메모보다 많은 정보를 줄 수 없다. 이 모델에서 "충실함"과 "새로운 울림"은 서로 맞바꾸는 관계다.

## 결정

1. **톤은 거울이다.** 한국어 해요체 한 문장(40자 안팎). 평가·조언·질문·이모지·느낌표를 쓰지 않고, 메모에 없는 사실·장면을 지어내지 않는다. 곡은 필요할 때만 이름으로 언급하고 가사·배경은 단정하지 않는다. 일기에서는 지어내기가 복창보다 더 해롭다고 판단해 **충실함을 우선**한다 (프롬프트에 "새 이미지·분위기 묘사 금지, 숫자는 그대로 옮김", 온도 0.3).
2. **가볍게 출시한다.** 위 한계(복창에 가깝고 어미가 단조로움)를 알고 출시하고, 기록에서 SQL로 계산한 사실(예: 이번 달 이 가수 N번째)을 재료로 주고 LLM은 문장만 만드는 방식으로 나중에 올린다. 사실이 DB에서 오므로 지어낼 수 없고 메모 밖의 정보를 더할 수 있다.
3. **메모가 없거나 5자 미만이면 코멘트를 만들지 않는다.** 재료 없이 만든 코멘트는 빈말이다. 달력에 빈자리가 생겨도 허용한다.
4. **마음이 많이 힘든 메모는 고정 문구로 대체한다.** 모델이 `{ comment, sensitive }`를 함께 반환하고, `sensitive`이면 모델 문장을 저장하지 않고 "오늘의 마음을 이곳에 적어두었어요."를 저장한다. 판별은 **애매하면 true**로 보수적으로 편향시켰다. 오탐의 비용은 고정 문구가 나오는 정도이고, 미탐의 비용은 힘든 사람에게 차가운 복창이 나가는 것이라 비대칭이기 때문이다.
5. **제공자·구조는 mood 제안과 같다.** Gemini 3.5 Flash-Lite 무료 티어(ADR-0005), `CommentGenerator` 인터페이스, 교체 지점은 `shared/lib/ai/index.ts`. 호출 공통부는 `geminiClient.ts`로 분리해 두 기능이 공유한다.
6. **생성은 서버가 맡는다.** 기록 저장 직후 `saveRecord`가 Next의 `after()`로 생성을 시작하고(응답을 막지 않음), 재시도는 `POST /api/ai/daily-comment { recordId }`로 한다. 서버가 DB에서 기록을 읽으므로 클라이언트가 내용을 위조할 수 없고, 본인 기록인지는 라우트에서 직접 확인한다(`records`는 공개 조회가 가능하다). 한 번 저장된 코멘트는 다시 만들지 않는다. 클라이언트는 도착할 때까지 폴링하며, 별도 상태 컬럼 없이 "메모 있음 + 코멘트 없음 + 생성 후 60초 이내"를 생성 중, 그 이후를 실패로 파생한다.

## 결과

**긍정적**

- 지어낸 사실이 일기에 섞이지 않는다. 힘든 날에 가벼운 응원이나 차가운 복창이 나갈 위험을 줄였다.
- 저장은 코멘트 생성을 기다리지 않는다. 실패해도 기록은 정상이고 재시도할 수 있다.
- 마이그레이션 없이 기존 `records.ai_comment`와 `records_update_own` RLS를 그대로 쓴다.

**부정적 / 트레이드오프**

- 코멘트가 단조롭다(어미가 "~던 순간이었어요"로 수렴). 온도를 올리면 다양해지지만 지어낼 위험도 커진다.
- `sensitive` 판별은 LLM 판단이라 안전장치가 아니다. 소규모 샘플(12~22건)에서만 확인했고 경계 사례에서 한 번 흔들렸다. 실사용자가 생기기 전에 보수적 규칙과 별도 안내를 다시 검토해야 한다.
- `ai_comment`는 `records` RLS상 공개 조회가 가능하다. 화면에서만 본인에게 보이고, 데이터 수준의 비공개는 아니다.
- 무료 티어 한도(분당 15회, 일 500회)를 mood 제안과 공유한다. 재시도 클릭도 한도를 쓴다.
- `after()`의 실제 동작은 배포 환경(Vercel)에서 확인해야 한다. 문제가 있으면 클라이언트가 생성을 요청하는 방식으로 되돌릴 수 있고, 서비스 함수는 그대로 재사용된다.

## 재검토 조건

- 사용자가 "코멘트가 복창 같다"고 느끼거나 코멘트를 읽지 않는 것이 관찰될 때 → 기록 기반 사실 재료 방식으로 업그레이드
- `sensitive` 오판(미탐)이 확인될 때
- 무료 한도에 자주 걸릴 때, 또는 실사용자가 생겨 데이터 사용 정책이 문제될 때 (ADR-0005와 동일)
